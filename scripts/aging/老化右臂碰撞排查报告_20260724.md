# TuyaRobot 老化右臂碰撞排查报告

## 1. 结论

本次右臂异常与“三组角度运动”直接相关，触发点已经定位为：

- 老化第 4 轮；
- `send_upper_angles`；
- 双臂同时运动；
- 插补模式 `0`；
- 从第 2 组角度切换到第 3 组角度；
- 第 3 组速度 `100`。

更准确地说，当前证据不能证明“第 3 组静态目标姿态必然自碰”，但可以确认双臂以速度 `100` 从第 2 组向第 3 组运动时，右臂 J1/J2 没有在目标附近正常减速停止，发生持续过冲、越过软件限位并产生大电流和电机错误。现场观察到的自碰很可能发生在这一异常过冲过程中。

本次事故还有第二个独立问题：监控线程在异常开始约 1.17 秒后已经读到右臂 J1/J2 过压，但脚本没有识别嵌套的错误状态，导致没有触发全局停止，事故后仍继续执行后续老化阶段和循环。

## 2. 第一性原理分析

机器人是否安全到达一个点位，不只取决于终点角度，还取决于：

1. 起始姿态；
2. 双臂是否同时运动；
3. 规划出来的中间路径；
4. 速度、加速度和减速能力；
5. 关节控制器当时的温度、负载和异常状态；
6. 脚本能否在首次错误或越界时立即停止。

因此，“右臂单独到达过第 3 组”只能证明该目标对单臂至少曾经可达，不能证明从任意起点以速度 `100` 双臂同时运动都安全。

## 4. 脚本未及时停止的原因

### 4.1 P0：错误状态解析漏掉真实结构

当前 `scripts/aging/tuya_aging/utils.py` 中的 `upper_status_has_error()` 只检查：

```text
status
left_arm_error
right_arm_error
```

实际 SDK 返回结构为：

```python
{
    "left": 0,
    "right": {
        "motor_errors": [
            {"joint_id": 1, "bitmask": 4096, ...},
            {"joint_id": 2, "bitmask": 4096, ...},
        ]
    },
}
```

错误位于 `right.motor_errors`，现有函数返回 `False`。所以 `upper_monitor.py` 虽然读取并打印了错误，却没有调用全局致命停止。

### 4.2 P0：运动阶段异常默认“记录后继续”

当前上半身运动 `_phase()` 对普通 `AgingError` 和 `TimeoutError` 的策略是记录后继续。动作 `568` 未到位后，脚本继续执行统一回零和后续阶段。

“单次通信超时可记录后继续”与“已经读取到电机错误、角度越界或严重未到位”必须分开处理。后三者是安全异常，不能套用连续 10 次失败才停止的普通通信策略。

### 4.3 P0：运动中缺少实时越界保护

第 3 组运动过程中，J1 在 `23:31:08.826` 已经到 `-171.98°`，越过软件下限，但等待逻辑主要依赖“是否停止”，没有根据实时角度越界主动急停。

## 5. 根因判断

### 已确认

1. 直接触发命令是双臂第 2 组到第 3 组、速度 `100` 的 `send_upper_angles`。
2. 右臂 J1/J2 在接近目标后没有正常停止，随后过冲。
3. J1 越过 `-166°` 软件限位。
4. 运动过程中产生了过压、大电流和后续控制/I²t 错误。
5. 脚本已经读到错误，但没有正确识别并停止。

### 高概率但尚需硬件侧确认

1. 速度 `100`、双臂同时规划、连续三组不回零和长时间老化累积状态共同放大了控制风险。
2. 自碰或机械阻挡导致后续大电流和卡滞。
3. 控制器在第 3 组路径中出现异常减速/位置闭环失效。

### 不能仅凭日志确认

1. 第 3 组目标姿态本身是否存在固定几何自碰。
2. 首因是固件规划、驱动器、编码器、制动机构还是机械结构。
3. 碰撞发生的精确机械接触位置。

## 6. 分级处置建议

### P0：再次运行前必须完成

1. 暂停双臂第 3 组速度 `100`，当前脚本不要再次整套真机运行。
2. 机器人仍处于卡滞或错误状态时，不要直接强制 `go_zero()`；先按厂商安全恢复流程断能、卸载或人工解除机械干涉并检查结构。
3. 修复嵌套错误状态识别：`left/right` 内存在非零状态、`motor_errors` 或明确错误时立即全局停止。
4. 运动中发现关节越过软件限位立即执行一次上半身急停并停止全部线程。
5. 明确机器人/关节错误、软件限位越界和严重异常角度必须立即停止，不受“连续 10 次通信/运动失败”阈值控制。
6. 动作未到位且同时存在错误状态或大幅越界时，禁止自动回零和继续下一阶段。

### P1：恢复验证前建议完成

1. 将“三组角度”拆成可单独选择的安全验证阶段。
2. 临时把双臂第 3 组速度降到 `10` 或 `20`，并增加组间稳定等待。
3. 分别验证：
   - 第 2 组到第 3 组的右臂单独运动；
   - 左臂单独运动；
   - 双臂低速运动。
4. 每项只执行一次，并要求人员在急停旁监护；确认路径、机械间隙和电流正常后才考虑逐级提高速度。
5. 增加运动过程采样：目标角度、实时角度、速度、电流、错误状态和软件限位余量使用同一时间戳关联。

### P2：长期老化改进

1. 给每组角度建立“起点—终点—速度—双臂/单臂”的路径安全矩阵，而不是只验证终点。
2. 对 J1/J2 增加速度和电流趋势告警。
3. 对同一目标连续出现过冲趋势时提前终止，不等待最终超时。
4. 报告中区分通信失败、未到位、安全越界、机器人错误和急停，不能统一归类为普通动作失败。

## 7. 建议的最小代码整改范围

本次仅排查，未修改运动代码。下一步若实施，建议最小范围为：

1. 修改 `utils.upper_status_has_error()`，兼容 SDK 当前嵌套状态结构。
2. 在上半身监控中同时检查 `get_upper_joints_status` 和 `get_upper_robot_status`。
3. 在等待运动结束期间加入实时错误和软件限位检查。
4. 将安全异常转换为 `SafetyViolationError`，直接触发全局停止。
5. 临时禁用双臂第 3 组速度 `100`，等待安全路径重新确认。
6. 增加模拟测试，验证嵌套电机错误、越界和大幅未到位均能立即停止。
